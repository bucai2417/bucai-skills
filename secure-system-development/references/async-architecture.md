# 异步优先架构

系统默认按异步设计：请求路径上只做「校验 + 必要的同步写」，其余（通知、报表、导出、第三方同步、重计算）全部走队列。这样单点故障不会拖垮接口，突发流量可以被吸收。

## 1. 基本形态

```
HTTP 请求 → 校验/鉴权 → 关键写库（事务）→ 写 Outbox/发消息 → 立即返回（task_id 或资源 id）
                                                     ↓
                                              Worker 消费 → 处理 → 更新状态 → 推送/轮询可见
```

- 明确每个接口的同步边界：必须同步的只有「用户马上要看到结果」的部分。
- 长任务返回 `202 Accepted` + `task_id` 或资源状态 `pending`，前端轮询/SSE/WebSocket 拿结果。
- 状态机要显式：`pending → processing → succeeded/failed`，失败可重试，前端有明确文案。

## 2. 超时（第一优先级）

- 每个外部调用都要有超时：HTTP client（连接 + 读取）、数据库（statement timeout）、Redis、MQ。
- 超时要分层：上游超时 > 下游超时，否则上游先断，下游还在白干。
- 不要依赖默认值，显式配置并在配置中心统一管理。

```ts
const res = await fetch(url, { signal: AbortSignal.timeout(3000) });
```

## 3. 重试

- 只重试**幂等**操作和**可恢复**错误（超时、连接失败、429、5xx）；不重试 4xx 业务错误。
- 指数退避 + 抖动：`delay = min(base * 2^n, cap) * (0.5 + random*0.5)`。
- 有次数上限；超限进死信队列并告警，不无限重试。
- 重试要有全局预算，防止「雪崩式重试」压垮下游（熔断 + 限流配合）。

## 4. 队列与消费

- 至少一次投递 → **消费必须幂等**：`UNIQUE(message_id)` 去重表，处理与去重在同一事务里。
- 需要严格顺序时才用顺序队列/单分区；否则并发消费提高吞吐。
- 失败隔离：毒消息（处理必失败）不能无限重投阻塞队列，超次进 DLQ 并人工介入。
- 可见性超时（visibility timeout）要大于最长处理时间，避免重复消费；处理时间不可控时用「租约续期」。
- 消息体带 `trace_id`、`created_at`、`schema_version`；结构演进保持向后兼容（新增字段可选，不删必填）。

## 5. 事务消息 / Outbox

- 不允许「写库成功后发消息」的裸双写：库成功、消息失败 → 数据不一致。
- 方案：业务写入与 outbox 记录在同一事务；CDC（Debezium）或轮询投递器把 outbox 发到 MQ，成功后标记；消费端幂等。
- 反过来（消息成功、库失败）同样不允许把消息当作唯一真相源，除非设计成事件溯源。

## 6. 限流、背压与降级

- 入口限流：网关按 IP/用户/接口维度；关键接口（登录、下单、发码）单独配额。
- 队列积压监控：长度、消费延迟；积压超阈值时降级（关闭非核心任务、拒绝低优先级请求）。
- 消费者并发与下游容量匹配：消费能力 > 生产速度才不积压，必要时动态扩消费者。
- 熔断：下游错误率超阈值直接快速失败（半开探测恢复），避免拖死整个调用链。
- 舱壁隔离：不同业务用独立线程池/队列，防止一个慢任务耗尽资源。

## 7. 分布式任务与锁

- 定时任务多实例部署要加锁（Redis `SET key val NX PX ttl` + 续期，或调度中心统一派发）。
- 锁必须有过期时间，并在业务超时时续期；释放时校验持有者（Lua 比较删除）。
- 关键：锁不能替代幂等，锁只降低并发，幂等保证正确性。

## 8. 事件循环与 CPU 密集任务

- Node/Python 异步模型里，一次同步阻塞会卡住所有请求：
  - 禁止在请求路径用 `fs.*Sync`、大 JSON 同步解析、`crypto` 同步大计算。
  - 重 CPU（图片处理、PDF 生成、压缩、加密大文件）放 `worker_threads` / 独立服务。
- 大文件用流式处理，不一次性读进内存。
- 单次查询/响应设大小上限，防 OOM。

## 9. 优雅停机

顺序：停止接收新请求（摘流量）→ 等待在途请求完成（有上限）→ 停止消费队列 → 提交/回滚事务 → 关闭连接池 → 退出。

- 处理 SIGTERM，设置停机超时（如 30s），超时强制退出。
- 容器编排的 `terminationGracePeriodSeconds` 要大于应用停机时间。
- 消费者停机时把未完成消息的确认留给下次（不要 ack 未处理完的消息）。

## 10. 错误处理与可观测性

- 全局兜底：`unhandledRejection`、`uncaughtException`、队列消费者未捕获异常 → 记录 + 指标 + 告警，绝不静默。
- 每个请求/消息生成 trace id 并贯穿调用链，日志结构化（JSON），带 `service`、`trace_id`、`user_id`、耗时。
- 指标：QPS、P95/P99 延迟、错误率、队列积压、消费延迟、重试次数、DLQ 数量。
- 告警要可执行：对应到具体处理手册，避免告警疲劳。

## 11. 前端侧的异步配合

- 提交后立即反馈（按钮 loading、任务已受理），不要阻塞等待长任务。
- 状态用轮询（带退避）或 SSE；WebSocket 仅在需要双向实时时使用。
- 超时/失败态要明确可重试，并且重试按钮本身要幂等（带幂等键）。
